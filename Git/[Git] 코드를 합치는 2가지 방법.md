여러 명의 개발자가 협업을 수행하면서 코드를 합쳐야 하는 경우가 발생한다.
이때 여러 브랜치를 머지하는 방법이 2가지이다.

# base
    서로 다른 브랜치의 부모가 되는 커밋.
    base를 기준으로 브랜치가 탄생한다.

# 1. fast-forward
    기준이 되는 브랜치에는 변경사항이 없고
    신규 브랜치에만 변경사항이 발생한 경우
    신규 브랜치가 main branch가 됨.
    fast-forward 즉 빨리 감기를 하여 새로운 커밋의 위치로 HEAD가 이동하는 것.
    merge commit 이력이 남지 않음.

# 2. 3-way-merge
    두개의 브랜치에 각각 변경사항이 발생한 경우 
    각각의 커밋을 모두 합친 하나의 커밋을 만는 방식 



# pull과 merge 차이
    pull은 원격 저장소의 변경사항을 로컬 저장소로 내려받아 합치는 것 
    git pull = git fetch + git merge

    merge는 서로 다른 브랜치의 내용을 합치는 것.


# rebase
    불필요한 머지 이력을 남기지 않기 때문에 깃에서 권장사항

- [Rebase과정]
ⓐ 일단 두 브랜치가 나뉘기 전인 공통 커밋으로 이동  
ⓑ 공통 커밋부터 지금 Checkout 한 브랜치가 가리키는 커밋까지 diff를 차례로 만들어 어딘가에 임시로 저장해 놓는다.   
ⓒ 'Rebase 할 브랜치'가 '합칠 브랜치'가 가리키는 커밋을 가리키게 하고   
ⓓ 아까 저장해 놓았던 변경사항을 차례대로 적용한다.  
ⓔ 그리고 나서 main 브랜치를 Fast-forward 시킨다. (=main  브랜치를 최신 커밋으로 옮긴다.)
 


# 한 줄기로 합치는 방식
// feature => main
// feature와 main은 모두 원격의 최신 커밋이 모두 동기화 된 조건

git checkout feature
git rebase main
    충돌 있으면 수정하기...
    리베이스 끝나면 Successfully 어쩌고 메시지 뜸...
git checkout main
git merge feature
git push origin main // 원격 main에 커밋 동기화

며칠에 걸쳐서 올렸던 커밋이 한 날짜로 고정되고
깃 그래프가 한 줄로 깔끔하게 정리됐다면 성공!


하지만 이미 원격 저장소에 올라간 커밋을 다시 리베이스 하면 난리가 날 수 있다.


git pull --rebase 옵션 사용을 권장한다.

그럼 혹여나 있을지도 모르는 중복 커밋을 git이 알아서 합쳐준다.


그리고 브랜치에서 하던 일을 완전히 마치고

메인 브랜치로 작업 내용을 보낼 준비가 되면 rebase를 하는게 좋단다.


Rebase 하면 뭔가 망할까봐 무서워요!
혹시 이러한 생각이 든다면, 하나만 생각하시면 됩니다.

공유하는 브랜치에서는 절대 Rebase 하지 않는다.

해당 룰만 지킨다면 rebase를 사용해서 문제가 생길 일은 없다고 장담합니다. 간단히 생각해서 내 커밋들의 베이스를 공유하는 브랜치 뒤로 옮긴다면 아무 문제가 없지만, 남들이 사용하는 커밋들의 베이스를 내 브랜치 뒤로 옮긴다면 난리가 나겠죠.

# Rebase를 사용하는 경우
로컬 브랜치에서의 작업
개별적인 기능 브랜치
Rebase는 개인적으로 작업하거나 아직 Push하지 않은 커밋에 사용하는 것이 좋습니다.

# Merge를 사용하는 경우
이미 Push한 브랜치에 대해서는 Rebase를 사용하지 않는 것이 안전합니다.
여러 명의 개발자가 협업할 때는 안정적인 Merge가 더 적절할 수 있습니다.
프로젝트의 중요한 이력을 남기고자 할 때 Merge를 사용합니다.
