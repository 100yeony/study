# 튜닝이 필요한 이유
    cpu, disk는 생각보다 빠르지 않다.
    cpu는 join과 관련되어 있고 
    disk는 read block, 인덱스와 관련이 있다.

# 해결책
    병렬로 늘리기. 단순 무식하지만 확실한 방법
    튜닝을 통해 cpu, disk가 할 일을 줄여주기.
    제일 좋은 해결책은 인메모리 디비를 사용하는 것.
    하지만 비용 대비 효용성(가성비)가 떨어지고
    데이터 정합성 문제가 발생할 수 있다.(disk 데이터와 메모리 데이터 간)

# 옵티마이저
    데이터를 가장 효율적으로 검색(where, disk i/o), 결합(join, cpu) 등을 하는 DB 행위
    가장 효율적인 실행 계획을 만들어주는 DB 엔진의 기능
    똑똑해지기 위한 2대 조건: 최신 통계 정보, 올바른 인덱스
    똑똑해지기 위한 조건이 불충분하다면 실행계획이 틀려짐.
    쿼리가 수행하는 업무가 일반적이지 않다면 실행계획이 달라짐.

# 튜닝
    옵티마이저가 만든 쿼리 실행 계획을 다시 한번 최적화하여 업무 목표 시간 내에 결과를 얻도록 만드는 사람의 행위
    옵티마이저가 만든 실행계획이 틀렸거나, 달랐을 때 하는 행위
    
    튜닝 단계
    - 입문: 옵티마이저, 통계정보, 인덱스에 대한 기초 지식 
    - 초급: 통계정보, 인덱스 조정(ex. table full scan, index full scan 제거 가능)
    - 중급: 조인 조건 수정, 쿼리 재작성, 힌트 추가(ex. 인덱스 추가. hash join을 nested loop으로 변경, with..select문 사용 등)
    - 고급: 설계 변경, 대용량 배치 쿼리 튜닝 

    튜닝: 쿼리의 elapsed time이 업무 목표 시간 안에 들어오도록 하는 것
    적절한 인덱스: 쿼리의 elapsed time이 업무 목표 시간 안에 들어오도록 하기 위한 필수 조건
    분포도: 인덱스를 적절하게 만들기 위해 분석해야 할 필수 요건
    옵티마이저 원리: 분포도를 분석하여 생성한 인덱스가 적정한지 분석
    
    옵티마이저가 만든 실행 계획이 틀린 겨우
        - 통계 정보가 없을 때
        - 데이터 증가에 따라 분포도가 달라져서 인덱스 스캔 -> 테이블 스캔으로 변경되는 경우
        - 실행 계획이 힌트로 고정되어 있을 때
    
    옵티마이저가 만든 실행 계획이 다른 경우
        - 변수에 들어오는 값의 범위가 일반적인 경우보다 좁거나 넓을 때(보통 1개월 조회하다가 간혹 1년치를 조회하는 경우)
        - 특수한 업무일 때(인덱스 스캔이 정상이지만 월/분기/연 보고서를 위해 테이블 전체를 읽어야 할 때)

## Execution Plan(실행 계획)
    옵티마이저가 특정 SQL 문을 실행하기 위해 수행한 일련의 동작(Operation)을 트리 형식으로 표현한 것
    - 쿼리를 수행하기 위해
        - 어떤 테이블을 기준 삼아
        - 어떤 키(인덱스)로 검색을 한 후(Access Path)
        - 어떻게 join된 다음 테이블과 결합해서(Join Method)
        - 이렇게 결합된 다음 테이블에서 어떤 key(인덱스)로 검색을 한 후
        - 어떻게 group by, order by 해서
        - 어떻게 출력(select 결과)를 보여줄 것인가?
    - is null VS. NULL
        - 우리 눈에는 똑같은 결과이지만 실행 계획은 다름
        - is null은 3줄, NULL은 4줄. 짧은 쿼리는 거의 차이가 없지만 큰 경우는 차이가 남
        - is null이 낫다.

## Index
    Index range scan
    index unique scan
    table scan(full scan)
    분포도(cardinality, NDV; Number of Distinct Values)
    - 한개의 컬럼에 들어있는 데이터 다양성
    - 데이터의 종류가 다양한 칼럼을 인덱스의 첫번째 칼럼으로 선택 
    - optimization 결과로 나오는게 분포도다? -> no
    - 분포도가 낮은 칼럼은 인덱스에 포함할 가치가 없다.
        * 분포도가 높다(1에 가깝다) = 같은 값을 가진다.
        * 분포도가 낮다 = 서로 다른 값을 가진다.
        - 분포도가 1인 칼럼은 절대 인덱스 걸 필요가 없음.(예. 한국 사람들 대상으로 국적: 대한민국)
        - 컬럼 값이 y/n, 0/1인 칼럼은 bitmap index를 이용할 수 있다. 다만 DML 시 block lock 발생하므로 DML 많은 테이블에 설계하지 말것.
    - 분포도를 고려해서 인덱스를 설계해야 한다.
        - 이름, 성 순으로 인덱스 걸어야 함.
        - 이름 수가 훨씬 많기 때문.
        실제 사례
            - (한중일) 성 + 이름 -> 이름 + 성
            - 강의연도 + 학기 + 강의일련번호 -> 강의일련번호 + 학기 (+강의연도)
            - 회사명 + 본부명 + 강의명 -> 부서명 + 본부명 + 회사명
            - 시,도 + 군,구 + 동 -> 동 
        분포도 낮은 순 -> 높은 순

    - 인덱스는 책 맨 뒤에 있는 찾아보기랑 같다. 목차와는 다름
    - 인덱스가 필요한 이유
        - 디스크가 느리기 때문에 원하는 데이터가 있는 블록을 빠르게 찾게 위함
    - 한 테이블에 일반적으로 인덱스 30개가 넘어가면 DML이 느려짐. 일반적으로10~개 정도
    - 인덱스 이름에 로마자 붙이지 말기. MEMBER_TBL_IX_I
    - 인덱스를 걸면 row id + 복제된 데이터의 새로운 세트가 만들어진다.
    - 인덱스를 무분별하게 걸면 똑같은 데이터가 계속 복제되므로 table space 용량 차지. 
        - DML할 때마다 찾아보기를 새로 만드는 정렬 작업이 발생하므로 전체 쿼리 실행 시간 느려짐.
    - 인덱스를 처음 만들 때 최적으로 만들어야 함. 돌이키기 어렵다.
