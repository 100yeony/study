# 파인튜닝(Fine-tuning)
- 사전에 학습된 모델(pre-trained model)을 새로운, 보통 더 작은 데이터셋(몇백GB, 몇TB)에 맞추어 추가 학습을 수행하는 과정
- 나의 데이터에 맞게 학습
- 입력, 출력 외에 학습시키는 부분에 대한 추가 비용 발생
- 학습시킬 때 상당히 많은 양의 텍스트 데이터여서 과금이 많이 되고 api 구매 시 많이 구입해야 학습할때 문제 없을듯.
- 정확성을 위해 데이터가 많으면 좋다.
- 하지만 데이터 형식을 맞추기가 어렵다. 다 수작업임. 그래서 파인튜닝을 많이 하는 곳이 없다. rag 사용


# RAG(Retrieval-Augmented Generation)
- 자연어 처리(NLP) 분야에서 사용되는 기술로, 정보 검색을 통해 언어 생성 과정을 향상시키는 방법
- 데이터 소스로부터 Prompt 또는 질문과 연관된 데이터를 가져오는 행위
- Retrieval = 연관 텍스트를 가져오는 행위(검색도 Retrieval의 일종)
- Generation = ChatGPT
- 실시간으로 부족한 데이터를 주입하기 위한 방법


# 어떻게 연관 정보를 가져올까? = RAG 핵심
- Retrieval = 연관 텍스트를 가져오는 행위 
방법
1. 단어 기반 방법론) 텍스트에서 특정 단어가 자주 발생 -> 그 단어가 관련 있을거다
    - 단순하게 단어 빈도 기반이라 실제 맥락과 상관 없음. 성능이 상대적으로 낮다.
2. 자주 발생하는 단어가 항상 자주 발생 -> 가중치 줄이기
3. 딥러닝 모델한테 텍스트 간의 문서를 직접 학습 -> 2012년 Word2Vec논문에서 시작. 흔히 임베딩이라고 함.

# 임베딩 Embedding
- 차원 수가 높을수록 보통은 성능이 더 높음
- 사과를 [0.2, -0.5, 0.7]로 표현
    - 3개의 숫자로 표현. 3차원 임베딩
- 128차원의 경우 128개의 숫자로 표현
- 보통 256~4096 사이의 차원을 사용. 384~1024 사이가 가장 흔히 사용됨.
- 차원 수가 높을수록 연산 시간 오래 걸리고 API 비용 높아짐

동작 구조
1. 사용자가 질문한다.(Prompt 입력)
2. RAG 로직을 통해 질문과 연관된 데이터를 가져와서 Prompt에 추가
3. ChatGPT는 추가된 데이터를 포함한 새로운 Prompt에 대해 답변

# ChatGPT가 모르는 지식을 채우는 방법. RAG가 최선일까?(다른 방법론들)
- 크게 보면 LLM 학습 단계에서 주입하거나
- 추론(답변)하는 단계에서 넣어줄 수 있음
    - 사전 훈련(Pretraining)
    - 파인튜닝(finetuning)
        - 비용 비쌈. 실시간 데이터가 아님.
    - RAG
        - 실시간 데이터 학습 가능.
    - Prompt Engineering
        - 외부 지식이 필요하므로 실시간으로 데이터 학습 불가하여 아웃.
- 정답은 없음. 실시간성이 높을수록 RAG가 빛나고, 그러지 않을 경우(새로운 지식 들어오지 않는 경우) 이전 단계에서 1회 학습으로도 해결이 가능할 수 있음.

작동 원리
1. 정보 검색 단계
- 사용자 질문이나 입력에 가장 관련성이 높은 정보를 DB(벡터 디비)나 인터넷에서 찾는다. 이 과정에서 질문에 답할 수 있는 콘텐츠나 문서를 선택하기 위해 유사도 검색 같은 기술이 사용됨
2. 언어 생성 단계
- 검색된 정보를 바탕으로, 생성 모델(GPT-3)이 답변을 생성. 생성 모델은 검색된 콘텐츠를 활용하여 보다 정확하고 정보에 기반한 답변을 만들어냄.

- 질문이 들어오면 벡터로 바뀜 
- 자료 벡터 디비와 질문 벡터를 비교. 유사도 검색 
- 데이터를 벡터디비로 변환하는 작업이 만만치 않음. RAG 구축에 3~10개월 정도 잡는다. 속도, 정확도 등

# 파인튜닝이 필요한 요건
- 특정 도메인에 최적화된 서비스가 필요할때. 의료, 법 등

# 파인튜닝의 제약사항
- GPU 필요. 데이터가 몇백 GB~수백TB 까지. 비용 이슈
- 얼마나 학습시켜야 원하는 결과가 나오는지 알기 어려움. 데이터 자체 검증이라던지 특성이 달라서 어느 누구도 판단할 수 없다.
- 데이터가 변경될 때마다 추가 학습 필요. 매달 바뀐다면 매달 추가 학습 필요. 
- 파인튜닝 하려면 고정 데이터가 필요함.
- 질문과 답변으로 구성된 데이터 준비. 파인튜닝할때 필요한 데이터 형태가 정해져 있다. 수작업으로 데이터 작업 필요. 
- 방대한 분량의 데이터 준비. 데이터가 적으면 말도 안되는 답이 나온다. 데이터가 충분하지 않으면 정확도가 떨어진다. 데이터가 충분하지 않으면 파인튜닝이 의미가 없다.
- 모델 비용. input, output 비용 외에 훈련 비용도 포함

# RAG가 필요한 요건
- 개인/기업 데이터를 LLM과 연계하여 서비스하고자 할 때
- 실시간 변화하는 정보를 반영해야 하는 경우(파인튜닝과 반대됨)
- 다양한 정보(DB, NoSQL, 문서 등)를 통합한 질의 응답 시스템을 구축하고자 할 때


# RAG vs. Finetuning
- RAG 장점: 추가적인 LLM 학습이 필요 없고, 추론(답변) 단계에서 Prompt에 추가하여 바로 답변 가능. LLM 학습이 필요하진 않은 상대적으로 저렴한 방법론.
- RAG 단점: 연관 정보가 추가되며 input token 수가 길어져 비용 증가
- fineTuning 장점: LLM 학습을 통해 외부 지식을 학습할 수 있음 
    - 외부 지식 외에도 태스크를 어떻게 잘 풀수 있는지도 추가 학습시킬 수 있음
    - 단점: 추가 학습 비용 발생. 데이터 많거나 모델 클 경우 GPU 많이 필요. 



# RAG 제약 사항
- 정보 검색의 정확도
    - return 받는 데이터의 정확도가 높으려면 검색 결과 데이터의 정확도가 높아야 함
- 처리 속도와 효율성
    - 속도가 가장 빠르게 나올 수 있는 요건을 고려해야 함
- 복잡도와 자원 요구사항 늘어남
- 정보 손실
    - 임베딩 벡터 변환 과정에서의 손실: 문서가 긴 경우 벡터 차원으로 변환이 어렵다. 전부 다 벡터화 되지 않을 수 있다.
    - 검색 과정에서의 손실: 질문과 문서 사이의 관련성이 떨어질 수 있음. 관련성이 없는 문서를 가져올 수 있음 -> reranking으로 해결 


- RAG는 추가적인 LLM 학습이 필요없는 가성비 좋은 방법론
    - 난이도 높을수록 RAG에 사용되는 임베딩을 학습해야 할 수는 있음
- 다만 RAG를 활용함으로써 LLM -> LLM+RAG 2step으로 늘어남
    - RAG에서 잘못된 정보를 가져올 수 있다는 risk. 잘못된 정보를 가져와 할루시네이션이 발생할 수 있음.
- 최근 들어 LLM의 input context 길이가 1M 이상으로 늘기 시작(GPT-3.5 기준)
    - 별도의 RAG 로직을 사용하지 않고, 모든 정보를 LLM 입력에 넣는 방식도 옵션이 될 가능성이 존재 -> 비용 발생하긴 함. 
    - The Needle in a Haystack : 책에서 한 구절을 찾아라
        - 입력을 주고 입력 내에서 특정 텍스트를 찾는 테스트


- 문장을 단어별로 쪼개는게 청킹, 쪼개진 단어는 청크
- 벡터디비에서 LLM으로 넘어가는건 관련있는 청크
- LLM은 질문과 벡터디비에서 검색된 관련있는 청크를 조합하여 사용자에게 답변해줌


- RAG는 실시간 데이터에 대해 벡터디비화하는 과정을 파이프라인으로 만들 수 있음
- 가상 근사치의 벡터를 가져오게 됨. 이때 청크가 넘어감

# RAG를 위한 검색 유형: 키워드 검색
- 사용자가 입력한 하나 또는 여러 키워드를 바탕으로 정보를 찾아줌
- 기후변화에 대해 검색했다면 정확히 기후변화와 매칭되는 문서 반환

# 검색 유형: 시맨틱 검색(Semantic Search)
- 고도화된 질문
- 사용자의 질문이나 검색어의 의미를 이해하려고 시도하는 검색 기술
- 사용자 의도를 파악하고 의미 이해에 중점을 둠
- 영화 추천 이라고 입력한다면 
1. 사용자 의도 이해: 단순히 영화 정보가 아니라 새로운 영화 정보를 궁금해한다는걸 이해
2. 관련 결과 제공: 사용자 위치, 최근 검색 이력, 현재 인기 있는 영화 등의 정보를 종합해서 개인화된 영화 추천 목록 제공
- 사용 사례
1. 웹 검색 엔진
2. 전자 상거래 플랫폼: 아마존, 이베이
3. 기업 내부 데이터 검색 
- 요즘에는 키워드 검색 보다는 시맨틱 검색이 더 많다.

# RAG를 위한 검색 유형: 벡터 검색(Vector search)

동작 원리

2. 벡터간 유사도 측정: 코사인 유사도, 유클리드 거리 등
3. 유사 항목 검색: 파이스, 엘라스틱 서치 등 사용

# 유사도 검색
- 주어진 쿼리 또는 데이터 항목에 가장 유사한 항목을 데이터베이스나 데이터 집합에서 찾는 과정
- 고차원 벡터 공간에서 수행
- 유사성 측정: 코사인 유사도, 유클리드 거리, 자카드 유사도 등

# 유클리드 거리
- 두 점 사이의 직선 거리를 측정. 두 점 사이의 최단 거리를 측정. 가장 직관적이고 일반적으로 사용되는 거리 측정 방식. 

# 코사인 유사도
- 각도가 중요. 두 벡터의 방향이 완전히 같다면 1을 갖고 90도로 직교한다면 0으로 관계 없음, 반대라면 -1이 됨 
- -1~1로 표현. 1은 완전히 같고, 0은 관련 없고, -1은 정반대
- numpy 라는 아주 빠르게 연산해주는 라이브러리 사용하여 구현
- 결과 숫자에 대해 절대적인 숫자보다는 주어진 텍스트 중에서 가장 높은지가 중요 (0.358, 0.186.. 이렇게 나온 경우)

# 맨해튼 거리
- 격자 모양 경로를 따라 두 점 사이의 거리를 측정. 직선으로 이동하는 대신 수평, 수직으로만 이동함. 

# 자카드 유사도
- 두 집합 간의 유사도를 측정. 두 집합이 공유하는 원소 비율로 측정. 

# 벡터 데이터베이스
- 고차원 벡터 데이터를 저장하고 이를 기반으로 유사성 검색을 수행할 수 있는 데이터베이스

주요 특징
- 고차원 벡터 저장
- 유사도 검색
- 인덱싱 기반 

벡터 데이터베이스의 주요 속성
- 벡터 저장 및 검색 지원
- 능숙한 유사도 검색 (코사인 유사도, 유클리드 거리 등)
- 임베딩 지원
- 실시간 처리
- 확장성(계산 부하 분산할 수 있는 수평 확장 지원)

RDB와 벡터db의 차이
- 데이터 구조: rdb는 테이블 형태의 구조화된 데이터, 벡터 db는 고차원의 벡터 데이터를 처리
- 쿼리 방식: rdb는 SQL을 통한 쿼리인 반면, 벡터db는 유사성 검색에 특화된 쿼리 방식을 사용
- 사례. rdb는 전통적 비즈니스 데이터 관리, 벡터db는 머신러닝 모델에서 생성된 데이터의 검색과 분석에 적합

# 벡터DB 검색
- 유사도검색과 MMR(Maximum Marginal Relevance)가 있음.

# MMR
- 검색 결과의 다양성을 강화하는 중요한 방법
- 기본 아이디어는 먼저 벡터 저장소에 쿼리하여 가장 유사한 fetch_k 개의 응답을 선택. 이후 fetch_k 응답 내에서 가장 다양한 k 응답을 선택.
- 시맨틱 검색의 제약: 다양성이 떨어짐. 사용자 의도 파악하기 위해 행위 데이터, 접속 시간대를 기반으로 하여 다양성 떨어짐. 이를 보완하기 위해 사용됨.
- ex. 흰색 버섯 종류에 대해 알려줘 라고 질의가 들어오면 처음 두 문서에서 가장 유사 결과를 반환. 하지만 그 뒤의 문서에 더 관련있는 내용이 있을 수 있는데 이를 놓칠 수 있다.


- 크로마나 MMR 중 뭐가 더 좋은지는 써봐야 함. 

# 벡터 DB 인덱스: FAISS
- 인덱스 생성 과정
1. 데이터 전처리 후 벡터 변환
2. 클러스터링: k-Means Clustering 
3. 인덱스 구축
    1. flat index: Brute-force search. 모든 경우의 수 계산. 가장 높은 정확도 제공하지만 계산이 많이 필요
    2. IVF(Inverted File Index): 속도와 정확도 좋음. 중간 크기~대규모 데이터셋에 적합. 각 파티셔닝의 중앙값(centroid)를 관리함으로써 계산 정확도, 속도 높임. nprobe=3이면 5개의 파티션 중 3개만 검색해서 지정한다는 의미.  
    3. Product Quantization: 메모리 사용 줄이기 위해 벡터를 압축하여 사용하기 때문에 매우 큰 데이터셋에 적합
    4. HNSW(Hierarchical Navigable Small World): 그래프 기반 인덱스로 고차원 데이터에 효율적.
4. 검색
    1. 정확한 검색: 가장 정답에 가까운 이웃을 찾아오지만 검색 속도 오래걸릴 수 있음.
    2. 근사 검색: 유사한(approximate)한 결과를 반환하지만 속도 빠름
5. 후처리: Reranking

파이스에 내장된 유사도 검색을 사용하지 않고 직접 랭체인의 IVF 인덱스 구성해서 사용할 수도 있음. 
인덱스 만드는게 쉽지는 않음. 하드웨어 자원도 많이 사용. 써도 속도 보장할 수 없다. 

# Reranking
- 쿼리를 하면 유사도 검색을 통해 문서 반환하는데 이때 유사도가 높은 순으로 랭킹 매겨짐. LLM 쪽으로 랭킹이 넘어감. 정말 중요한 자료만 넘길 수 있도록 하는 작업.

필요 이유
- 검색 시간 단축을 위해 ANNs(Approximate Nearnest Neighbor search) 기술을 활용하기 때문에 질문과 관련없는 문서가 검색될 가능성이 높음. 거리 계산으로 하기 때문.. 

# kNN vs. aNN
- kNN(k-Nearest Neighbor)
    - prompt와 유사한 k개의 이웃을 찾는 것
    - k가 일정 수치 넘어갈수록 속도가 느려짐
- aNN(approximate Nearest Neighbor)
    - 정확도를 희생하고 속도를 챙긴 방법
    - 대규모 데이터 안에서 검색해야 하는 경우 많이 사용되는 방법론

해결 방법
1. 검색으로 반환되는 문서 수 늘리기. 기존에 1~3번까지 문서 보냈다면 1~300개 문서를 보내는 방식. 하지만 현실적으로 어려움. 확률을 높이는 것. 큰 의미가 없다. 토큰 제약 등
2. reranking : 관련 정보가 컨텍스트 내 상위에 존재하도록 함. 랭킹을 다시 조정하는 것. 마지막 후처리 과정임. 

구현
- 랭체인 프레임워크의 cohere 라이브러리로 할 수 있음
- 서비스 개발 시 유로, 테스트는 제약 많지만 무료.

검색기를 벡터디비에서 제공하는걸 선택할 수 있지만 cohere로 구현된 reranking 검색기를 넘길 수도 있음.

rag에서는 검색이 핵심임.
